# Rich AI Chat — handoff for the next agent

Rich AI Chat is a local-first agent prototype for KakkoiSchool. The goal is a flexible assistant that can research questions with sources, show images, charts, diagrams, videos and eventually music, and build and revise small desktop-style apps and games. It should also remember objectives, keep a visible todo list, and resume or coordinate long-running work. DeepSeek Flash is a hosted reference; GPT-OSS 20B and the Gemma 4 models exercise the local path, down to E2B. The product should accept ordinary language and novel requests without users learning benchmark-specific wording.

Clock and current facts should come from tools, and search results are untrusted data. Video search currently returns previews and watch links; music discovery/playback is future work. Do not imply media generation or that arbitrary URLs can be embedded.
- `src/lib/artifact-{build,checks,edits,primitives}.ts` contains build guidance, static checks, edits and reusable behavior. `src/html-artifact.tsx` provides the isolated preview and runtime diagnostics. Prefer a verified primitive for common behavior and let the model compose and adapt it; keep the general generation path for new tasks. Revisions target the selected artifact, preserve working behavior and keep the previous version available. GitHub PR creation and general workspace edits are future capabilities.
- `src/chat-page.tsx` and `src/lib/local-storage.ts` handle chat UI and browser persistence. Chat history is browser-local; no private transcripts are needed to diagnose or run evaluations. Use synthetic prompts and server diagnostics that exclude prompt text and credentials.

Suggested first milestone: a Basecoat-backed Kakkoi theme consumed by Rich AI Chat, an OpenUI coverage gallery, and one generated mini-app that can go full screen, save its editable source and install as a PWA. ## Recovery: what to borrow from PLH

The primary PLH checkout is `/Users/kakkoidev/Code/pi-local-harness`. Start with `harness/extension.mjs`, `watch.mjs`, `stuck.mjs` and `task-box.mjs`. Pi provides thinking, tool execution, agent lifecycle and settlement hooks. PLH combines repeated-reasoning and repeated-action checks with a bounded wake-up and retains enough context to resume the task. Its idle check is gated on the thinking phase, so copying that check alone would not catch a stall after the first answer token.

Rich AI Chat uses AI SDK streams. It previously exposed the first token and then treated any published text as a reason to refuse retry. `src/lib/chat-attempt.ts` now separates opening, answer and tool deadlines; whitespace, hidden thinking and half-written tool arguments don't extend them. Buffer answer text until a successful finish so partial OpenUI code or prose cannot leak into a replacement. Keep tool activity visible. Retry at most once before a tool has executed, with the same conversation context and an explicit recovery nudge. Reuse captured sources for tool-free synthesis; use captured media/clock output where available. Never replay a tool after it might have run. Keep the total/step ceilings and explicit cancellation. A local model may still fail to recover; distinguish that from a stuck interface.

The offline tests inject stalled streams through the actual AI SDK adapter under all five model IDs and check short completed replies, abandoned tool arguments, retained tool output and client cancellation. These are fault-injection tests, not live model passes. Pay attention to time-to-first-answer on slower MLX models now that text is buffered. If progress feedback is needed, show a status independent of the answer. Future workspace writes need persisted action IDs and receipts before enabling retries.

## Next feature: todos and long-running jobs

Use [Notes Keeping](https://github.com/KakkoiDev/notes-keeping) as a product reference. Its Claude Code plugin saves objectives, updates and todos in per-session Markdown, surfaces them in a panel, tracks status changes, and can continue unfinished items in a new session. Reuse those concepts and consider a Markdown import/export adapter. Do not make the Claude Code panel or transcript format a dependency of this web app. Use PLH as the reference for validated status transitions, recovery and verification.

1. Add a user-visible **Tasks** panel with the objective, open and completed todos, status, latest checkpoint, and links to outputs. Start with one persistent local task per chat when requested, editable by the user. Use a server-side store (SQLite is a candidate), separate from browser history. Give every task and item a stable ID; scope reads and writes to the owning user or local profile. Keep an append-only change log and exportable Markdown.
2. Give the agent small validated operations: read the active plan, propose or update items, and record a checkpoint or verification result. Put only the active objective, next actionable items, and relevant checkpoint into model context. The host rejects illegal transitions and conflicting writes. The agent cannot mark a result verified without the corresponding test, artifact or receipt. Treat imported notes and web content as untrusted data.
3. Add a background worker separate from the chat HTTP request. Persist job, run, attempt, lease, heartbeat and outcome. Model statuses such as queued, running, blocked, succeeded, failed and cancelled explicitly. Closing a tab does not stop a job; user cancellation does. On restart, reclaim expired leases and continue from the last committed checkpoint. Use stable operation IDs and reconcile unfinished external actions before replay. Only run independent tasks concurrently, with a small per-provider cap and one active generation per constrained local model by default. Expose which tasks are waiting and why.
4. Later, connect scoped file editing and preview/test tools. Keep each project in an isolated workspace, show the proposed diff, and request explicit authorization before publishing or opening a GitHub PR. Apply the same boundary to any new side-effecting tool; a todo is a plan, not permission to publish.

The first acceptance check is a user creating a two-step plan, seeing it in the panel, completing one step with evidence, and reopening the chat to find the remaining step and checkpoint. Then test an interrupted worker, duplicate delivery, cancellation, blocked dependencies, concurrent edits and cross-profile isolation. Once deterministic checks pass, add live evaluations for planning and resuming with novel tasks across the five models.
